## 一、文件上传验证问题

### 1.1 txt 文件上传验证失败

**问题描述**：
上传 `.txt` 文件时，后端报错：
```
Validation failed (current file type is text/plain, expected type is /(pdf|docx|txt|md)$/)
```

**根本原因**：
`FileTypeValidator` 检查的是文件的 MIME 类型，而非扩展名。浏览器的 `text/plain` MIME 类型无法被正则 `/(pdf|docx|txt|md)$/` 正确匹配。

**影响版本**：
- 前端上传 `.txt` 文件时验证被拒绝

**修复方案**：
创建自定义 `FileExtensionValidator`，检查文件扩展名而非 MIME 类型：

```typescript
// src/common/validators/file-extension.validator.ts
export class FileExtensionValidator extends FileValidator<FileExtensionValidatorOptions> {
  private readonly allowedExtensions: string[];

  constructor(options: FileExtensionValidatorOptions) {
    super(options);
    this.allowedExtensions = options.extensions.map((ext) =>
      ext.startsWith('.') ? ext.slice(1) : ext,
    );
  }

  isValid(file?: Express.Multer.File): boolean {
    if (!file || !file.originalname) {
      return false;
    }
    const extension = file.originalname.split('.').pop()?.toLowerCase();
    return extension ? this.allowedExtensions.includes(extension) : false;
  }

  buildErrorMessage(): string {
    return `Invalid file type. Allowed extensions: ${this.allowedExtensions.join(', ')}`;
  }
}
```

**修复文件**：
- `src/common/validators/file-extension.validator.ts` (新增)
- `src/modules/material/material.controller.ts` (引用新验证器)

**提交**：`a839711 fix: 修复 txt 和 md 文件上传处理问题`

### 1.2 md 文件处理失败

**问题描述**：
上传 `.md` 文件后，后端报错：
```
Unsupported file type: application/octet-stream
Material xxx status updated to FAILED
```

**根本原因**：
1. 浏览器上传 `.md` 文件时，部分情况下 MIME 类型被检测为 `application/octet-stream`
2. 虽然文件验证通过（扩展名正确），但内容处理器不支持 `application/octet-stream` 类型
3. `ContentExtractor.supportedMimeTypes` 不包含 `application/octet-stream`

**影响版本**：
- 上传 `.md` 文件后，状态一直为 `PARSING`，最终变为 `FAILED`

**修复方案**：
在 `ContentExtractor` 中添加 `resolveMimeType` 方法，当 MIME 类型未知时根据文件扩展名检测真实类型：

```typescript
// MIME type to extension mapping for fallback detection
private static readonly mimeTypeFromExtension: Record<string, string> = {
  '.pdf': 'application/pdf',
  '.txt': 'text/plain',
  '.text': 'text/plain',
  '.md': 'text/markdown',
  '.markdown': 'text/markdown',
  '.docx': 'application/vnd.openxmlformats-officedocument.wordprocessingml.document',
};

private resolveMimeType(filePath: string, mimeType: string): string {
  // If mimeType is already recognized, use it
  if (ContentExtractor.supportedMimeTypes.includes(mimeType)) {
    return mimeType;
  }

  // Try to detect from file extension
  const ext = path.extname(filePath).toLowerCase();
  const resolvedMime = ContentExtractor.mimeTypeFromExtension[ext];
  if (resolvedMime && ContentExtractor.supportedMimeTypes.includes(resolvedMime)) {
    this.logger.debug(`Detected mime type ${resolvedMime} from extension ${ext}`);
    return resolvedMime;
  }

  // Fallback to original mimeType if no match found
  return mimeType;
}
```

- `src/modules/material/processors/content-extractor.ts`

## 二、PDF 解析问题

### 2.1 pdf-parse v2 API 变更

**问题描述**：
PDF 文本提取失败，错误信息：
```
TypeError: PDFParse is not a constructor
```

**根本原因**：
`pdf-parse` v2 版本 API 变更，不再使用默认导出函数，而是导出 `PDFParse` 类。

**旧版用法（v1）**：
```typescript
const pdfParse = require('pdf-parse');
const data = await pdfParse(buffer);
```

**新版用法（v2）**：
```typescript
const { PDFParse } = await import('pdf-parse');
const parser = new PDFParse({ data: buffer });
const result = await parser.getText();
```

**修复方案**：
更新 `extractPdf` 方法：

```typescript
private async extractPdf(filePath: string): Promise<string> {
  const { PDFParse } = await import('pdf-parse');
  const buffer = await fs.readFile(filePath);
  const parser = new PDFParse({ data: buffer });
  const result = await parser.getText();
  return result.text || '';
}
```

**修复文件**：
- `src/modules/material/processors/content-extractor.ts`

## 三、消息队列问题

### 3.1 BullMQ 全局失败处理 job.data 为 undefined

**问题描述**：
BullMQ 全局失败处理器收到 `undefined` 的 `job.data`：
```
[Nest] ERROR [MaterialProcessor] Job failed with no materialId: undefined
```

**根本原因**：
某些失败场景下（如手动删除队列中的任务），`job.data` 可能为 `undefined` 或 `null`。

**修复方案**：
使用可选链操作符安全访问 `job.data?.materialId`：

```typescript
@OnGlobalQueueFailed()
async onQueueFailed(job: Job, error: Error) {
  const materialId = job.data?.materialId; // 安全访问
  if (materialId) {
    await this.materialService.updateParseError(materialId, error.message);
  }
}
```

**修复文件**：
- `src/modules/material/processors/material.processor.ts`

## 四、测试相关问题

### 4.1 Jest testMatch 无法找到测试文件

**问题描述**：
执行 `pnpm test` 时，部分测试文件（如 `material.controller.spec.ts`）未被找到。

**根本原因**：
Jest 配置的 `testMatch` 模式在某些环境下无法正确匹配嵌套在 `__tests__` 目录中的测试文件。

**解决方案**：
将测试文件移动到与源文件相同目录，使用 `.spec.ts` 后缀：
- `__tests__/material.controller.spec.ts` → `src/modules/material/material.controller.spec.ts`

**验证命令**：
```bash
pnpm test  # 不带参数，直接运行所有测试
```

## 五、启动脚本问题

### 5.1 PowerShell 脚本执行策略限制

**问题描述**：
在 Windows 上执行 PowerShell 脚本时可能被拒绝：
```
无法将 '.' 应用于加载配置文件，因为在该运行模式下不支持
```

**根本原因**：
PowerShell 执行策略（Execution Policy）限制了脚本运行。

**解决方案**：
使用 `-ExecutionPolicy Bypass` 参数执行脚本：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\start-all.ps1
```

**或使用 CMD 脚本**：
```cmd
scripts\start-all.cmd
```

## 六、Git 相关问题

### 6.1 CRLF 与 LF 换行符警告

**问题描述**：
Git 提交时出现警告：
```
warning: in the working copy of 'frontend/package.json', LF will be replaced by CRLF the next time Git touches it
```

**原因**：
Windows 系统默认使用 CRLF，而 Git 仓库配置为 LF。

**解决方案**：
项目根目录创建 `.gitattributes` 文件：
```
* text=auto
*.ts text eol=lf
*.tsx text eol=lf
*.json text eol=lf
*.md text eol=lf
```
